# Sprout: project rules

- The spec is docs/PLAN.md. If code and plan disagree, stop and ask.
- TypeScript strict. No `any`, no `@ts-ignore`, no non-null `!` on data from storage.
- All randomness goes through `src/engine/rng.ts`. Never call Math.random().
- All dates go through `src/lib/clock.ts` so tests can freeze time.
- All persistence goes through the `Repo` interface. No direct localStorage or IndexedDB calls in components.
- All speech goes through `src/audio/speech.ts`.
- Every storage write is awaited inside try/catch and surfaces a visible error state on failure.
- One React component per file, one default export, file name matches component name.
- Every route is registered in `src/app/routes.tsx` and nowhere else.
- The repo is public. No secrets, no email addresses and no real names in it, in code, tests, fixtures or commit messages. Secrets live in Cloudflare Worker settings and in `.dev.vars`, which git ignores.
- Every `/api` route except the sign-in routes checks the session before doing anything else.
- The Worker reaches D1, R2 and email only through the interfaces in `worker/store.ts` and `worker/mailer.ts`, so tests run with in-memory versions.
- The Worker never reads or changes the backup file's contents. Merging happens on the device.
- No GitHub Actions. The Cloudflare build runs `npm run verify` before every deploy.
- No `window.open`. External links use `<a target="_blank" rel="noopener noreferrer">` and exist only in parent mode.
- Kid screens: tap targets at least 64px, no text-only instructions below grade 1, no timers unless the parent turned the timer on, nothing that moves away before the child answers, no negative sounds.
- Layout: mobile first, flex column, scroll inside panels, never horizontal page scroll. Use `dvh`, not `vh`.
- Every new skill needs: a generator file, a catalogue row, and a pass from the generator test suite.
- Before finishing any phase run the audit in section 13 of the plan.
- The score is called "Skill Score" everywhere in the app. Never show the word SmartScore.
- The main device is an iPad running the app from the Home Screen. Follow the iPad rules in section 3.
- Never change what an existing seed produces without bumping that skill's version and its golden file.
- Day boundaries use `localDay()` from `src/lib/clock.ts`. Never work out a day from a UTC string.
- A `listen` question never shows its target and its options never speak. A `read` question never speaks the words the child must read.
- Saved references are skill ids, never positions in a list.
- Kid navigation replaces history. It never pushes a new entry.
- Dev routes exist only when `import.meta.env.DEV` is true.
- Spoken text is built from `Say` parts. Letters, numbers, times and money are typed parts, never digits or symbols inside a string.
- New fields on a stored record always have a zod default, so old records still load.
- Colours are named once: UI colours in `src/styles/tokens.css`, colours a child is asked about in `src/content/data/colors.ts`, picture colours in `src/visuals/palette.ts`. No colour is written anywhere else.
- Component style files hold no pixel or rem sizes. Sizes, borders and icon sizes are tokens in `tokens.css`.
- Screens use the shared components in `src/components/` (`BigButton`, `LinkButton`, `TextField`, `Notice`, `FormCard`, `FormLinks`, `SkillTile`, `TileGrid`, `Tabs`, `Column`, `FullScreenCard`, `QuestionStage`, `HoldButton`). A screen never writes its own `<button>`, `<label>` or alert box. `tests/repo/style.test.ts` enforces these three rules.

## Working rules for every phase

- Do exactly one phase per session. Stop when its gate (plan section 12) passes and report the gate output.
- Run `npm run verify` before saying a phase is done, and paste the result.
- If the gate fails, fix the cause. Never weaken, skip or delete a test.
- Do not add a dependency that is not listed in plan section 3. Ask first.
- No placeholders, no TODO stubs, no mock data in shipped screens.
- Commit at the end of the phase with message "Phase N: <name>".
- Ask the owner in multiple-choice form before deciding anything the plan leaves open. Do not assume.
- A push to `main` deploys the family's live app. Push only when the owner asks.

## Build status

- Step 1, Phase 0 (scaffold), is built.
- Step 2, Phase A (hosting and sign-in), is built: the scaffold gaps, `wrangler.jsonc`, `worker/`, `account.ts`, the SignIn and SetPassword screens and the sign-in guard. Until Phase 3 adds the device record, the app asks the server for the session at every launch, so it does not open offline yet.
- `APP_ORIGIN` is a plain setting next to `ENVIRONMENT`. The Worker compares the `Origin` header of every write against it.
- Local run: copy `.dev.vars.example` to `.dev.vars`, run `npx wrangler d1 execute sprout --local --file worker/schema.sql` once, then `npm run dev:worker` and `npm run dev`. The sign-in code is printed in the Worker's terminal.
- The app is live at `https://sprout.logstocks.com`. Workers Builds is connected to this repo: a push to `main` runs `npm run verify`, then `npx wrangler deploy`.
- Browser tests were brought forward from Phase 4a at the owner's request. `npm run e2e` builds the app, starts the real Worker locally over HTTPS with a throwaway database, and drives every account screen in WebKit (iPad landscape, iPad portrait, phone, 360 px) and Chromium. `npm run e2e:live` runs read-only checks on the live site and never asks for a code. Neither runs in `npm run verify` or in the cloud build. Every new screen and button gets a browser test in the same phase.
- `public/_headers` sets the safety headers for pages and files. A Cloudflare redirect rule, for the Sprout address only, sends plain http to https.
- Step 3, Phase 1 (engine core), is built: `rng`, `seed`, `types`, `check`, `validate`, `canonical`, `describe`, the registry, twelve oracles in `tests/oracles/`, the 300-seed generator and oracle harnesses, golden files, and three reference skills (M-PK-A2, M-K-B3, M-K-C4).
- To change what a skill produces: raise its `version` in `catalogue.ts`, then run `npm run golden`. The golden test refuses a change without a version bump.
- A generator returns a `QuestionDraft`. The registry adds the skill id, level, seed and key.
- M-PK-A2 level 2 uses the `dice` layout. The plan says "grid", but a 5-wide grid of 1 to 5 objects is the same picture as a row.
- Step 4, Phase 2 (scoring and adaptive), is built: `skillscore`, `review`, `recommend` with trouble spots, `diagnostic` with sittings, `merge`, `awards`, `ladders.ts` with all 140 skill ids, and the zod record schemas in `src/storage/schema.ts` (written here because the engine needs the record types; Phase 3 adds the repos).
- Engine code reads dates only through `src/lib/clock.ts` (`localDayOf`, `addDays`, `daysBetween`). A test fails on `new Date` or `Date.now` inside `src/engine` or `src/content`.
- A ladder walk in `DiagnosticProgress` also saves `right` and `wrong` for the skill being tested, so a diagnostic stopped in the middle of a skill resumes exactly.
- `evaluateAwards(states, totals, skills)` takes the catalogue as a third argument.
- Step 5, Phase 3 (storage), is built: the `Repo` interface, `memoryRepo` and `idbRepo` over one shared rule layer (`repoCore.ts` on a plain `Backend`), quarantine, reset, export and import with merge, the persistent-storage request, the error list and the sign-in state in the device record.
- Launch rule: a saved end date that has not passed opens the app with or without a network. One that has passed locks it. If the server says the session is gone, the app stays open for that launch, clears the saved sign-in in the background, and locks at the next launch.
- To add an IndexedDB change: add a new step to `UPGRADES` in `idbRepo.ts`. Never edit a step that has shipped.
- In tests, every test starts with an empty `memoryRepo` (`tests/setup.ts`), and `stubServer()` freezes the app clock to the test server's clock.
- Step 6, Phase 4a (visuals), is built: one drawing component for each `Visual` kind in `src/visuals/`, `VisualView` to draw any of them, pure geometry in `geometry.ts`, the colour list, and the dev-only gallery at `/dev/gallery`.
- `npm run e2e:gallery` draws the gallery in WebKit, checks every picture fits its frame and has a label, and saves `review/gallery.png` (iPad width), and a phone-width copy plus one image for each section under `.e2e/gallery/`. Look at them after any change to a picture.
- A diamond is drawn as a square standing on a corner, so `canonical.ts` treats it as a square turned 45 degrees.
- Clock hands stop short of the numbers. A browser test fails if a hand reaches them.
- Step 7, Phase 4b (question types and audio), is built: the eight question components and `QuestionView` in `src/items/`, `say`, `speech`, `clips`, `sfx` and `mute` in `src/audio/`, `scripts/make-clips.sh`, and the `/api/voice-pack` route.
- A question component reports the child's answer so far through `onChange`, or null while it is incomplete. The screen owns Submit. Give `ItemView` a `key` that changes with the question.
- A picture's spoken label is said on tap, except in a `listen` question. `speakable()` in `itemProps.ts` is the one place that decides.
- `npm run clips` makes the voice pack on the Mac and uploads it to R2. It was run on Nov 15, 2026 (132 clips). The pack's version is the R2 object's etag. A signed-in device downloads it in the background at launch.
- Step 8, Phase 5a (practice flow), is built: the install guide, child setup, the profile picker, a first home with a tile for each ready skill, the practice screen with its status panel, the explanation panel, milestone celebrations, the soft break, and attempts saved with a snapshot and local day.
- `usePractice` (in `src/app/`) runs one child on one skill. Each answer is saved (attempt, skill state, session) before the next question shows. A failed save keeps the question and reuses the same attempt on retry, so nothing is saved twice.
- Child setup opens from the profile picker for now. Phase 8a moves it behind the PIN gate.
- Browser tests are silent: `e2e/support/fixtures.ts` swaps the page's voice for a silent stand-in and removes audio output. A test checks that it is in place.
- Step 9, Phase 5b (kid navigation and lessons), is built: home with the daily goal ring, Play and today's picks, subject pages with grade tabs, the lesson player (four beats, and an example shown step by step), review sessions, the kid lock, the daily limit screen and the screen wake lock.
- `childDay.ts` (in `src/app/`) works out a child's day in one place: picks, answers and minutes today, reviews due, and whether the daily limit is reached. Home, Play, Review and Practice all read it. Minutes are the sum of the day's answer times.
- Kid lock: leaving practice or a review takes a 2-second hold (`HoldButton`). The step from the profile picker to home is the only history entry kid navigation adds. While a child is chosen, `App.tsx` never draws a step back in history: it keeps the screen as it was and steps forward again.
- The daily limit is checked on the way into home, a skill, Play and review, never in the middle of a question.
- A review answer is saved with kind `review` and does not move the score. The result of all 3 is applied once, after the last one (`useReview`).
- Play fixes its picks when it starts. A review pick runs as a review of that one skill.
- A child sees picks only from skills that are ready. With three skills so far, a grade 1 child has no picks and reaches skills through the Math page.
- Browser tests answer a question only after `[data-phase="asking"]` shows, because the last question stays on screen during the praise.
- Not covered by a browser test: the daily limit screen, because no screen sets daily minutes until Phase 8b. Unit tests cover it.
- Step 10, Phase 9 (offline and updates), is built: the service worker (made by `vite-plugin-pwa` at build time, settings in `vite.config.ts`) keeps every app file on the device, and `src/app/updates.ts` finds and applies new builds.
- The service worker has no route for `/api`, and page loads under `/api` are on its deny list. Never add a runtime cache for `/api`.
- Updates: the app asks for a new build at launch and when it returns to the front, at most once an hour. A new build waits. On `/` or `/home` (`isSafeToUpdate`) `App.tsx` tells it to take over. A browser can be slow to hand over, so the page is loaded again only once the new build is in charge and the app is on one of those two screens. Add a screen to that list only if nothing a child is doing can be lost there.
- While a new build is taking over, the app starts no backup sync: a request on its way delays the hand-over in Chromium.
- `/sw.js` and `/index.html` are served with `Cache-Control: no-cache` (`public/_headers`), so a new build is always seen.
- Browser tests block the service worker in every project except `offline-chromium`, which runs `e2e/offline.spec.ts`: offline reload and practice, and a new build arriving in the middle of a question.
- Step 11, Phase 10 (backup sync), is built: `worker/backup.ts` (`GET` and `PUT /api/backup`), the backup store in `worker/store.ts`, `src/storage/sync.ts`, `gzip.ts`, the first-sync screen on a new iPad, and `BackupStatus` for the data screen.
- The backup is one gzip file in R2, `family.json.gz`. Its version is the R2 etag. An upload names the version it was built on in the `X-Backup-Base` header (`none` for the first). R2 checks that as part of the write, so two iPads cannot overwrite each other.
- One sync run: fetch (skipped by the server if this device has the current version), check and merge with the import code, upload if `dirty`, and on a refusal fetch, merge and retry, 3 rounds at most. `dirty` is cleared before the export and set again if the upload fails, so a change made during the upload is never lost.
- A server file that cannot be read is never merged and never overwritten from the device (`badFile`). The parent is told to export a copy.
- When sync runs: at launch, when the child is back on the picker or home, and when the app returns to the front on one of those two screens. At most once every 5 minutes (`syncIfDue`). `syncNow` ignores the 5 minutes.
- After a sign-in on a device that has never synced, `FirstSync` runs one sync before the profile picker.
- The device record is changed by several background jobs. App code changes it only with `repo.updateDeviceState({ field })`, which takes turns with every other write. Never read it, wait, and write the whole record back.
- Every browser-test address belongs to one test family, so all tests would share one backup. By default `e2e/support/fixtures.ts` answers `/api/backup` with "no file". `test.use({ realBackup: true })` turns the real one on; such a test names its child with `freshName()`. The offline project needs it, because Playwright's request interception stops a new service worker taking over.
- `BackupStatus` is built and tested but not on a screen yet. Phase 8b puts it on the parent data screen.
- Step 12, Phase 6a (Math pre-K), is built: all 16 skills, in `src/content/generators/math/pk/`. `parts.ts` holds what they share; `findNumber.ts` and `moreFewer.ts` each make two skills. `CATALOGUE_VERSION` is 2.
- Pre-K categories: A. Counting, B. Comparing, C. Shapes and sizes, D. Patterns and sorting. The plan gives the letters, not the names.
- A question that turns on telling two colours apart (D.1, D.2, D.3 at level 1) takes its colours from `twoClearColors`, which leaves out pairs that are easy to mix up on a screen. The plan names two such pairs; the list in `parts.ts` adds six more.
- Dot cards use ⚫, and 🔴 with 🔵 for two colours. A heart's fact line ("two round tops and a point at the bottom") is not in the plan's shape facts.
- A counting skill whose answers sit near the top of its range passes `preferMiddle` to `nearbyNumbers`, or the answer lands on the last option too often.
- Sorting: with an item in hand, a tap anywhere in a group drops it there, even on a picture already inside.
- `e2e/prek.spec.ts` saves a score straight into IndexedDB to reach each skill's hardest level, then checks the layout at every size. Copy it for each content step.
- Not covered by a browser test: a correct answer at the hardest level of each skill. The 300-seed suite and the oracles cover correctness.
